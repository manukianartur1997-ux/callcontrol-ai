# CallControl — пилотный мульти-тенант SaaS

Бэкенд пилота: **Supabase** (Postgres + Auth) для данных и входа,
существующий **Cloudflare Worker** — для всего, что нельзя доверить браузеру
(AI-ключи организаций, вебхуки телефонии, учёт квоты).

Стратегия и решения — в [`../SAAS_PILOT_PLAN.md`](../SAAS_PILOT_PLAN.md).

## Что здесь

```
saas/
  migrations/
    0001_core.sql        схема, роли, RLS-политики, квоты
    0002_onboarding.sql  RPC: создание орг, приглашения, my_context
  test/
    00_supabase_shim.sql заглушка auth.users / auth.uid() для чистого Postgres
    01_rls_isolation.sql 20 тестов изоляции и иерархии ролей
    run.sh               поднимает Postgres в Docker и прогоняет всё
```

## Проверка

```bash
./saas/test/run.sh
```

Поднимает одноразовый Postgres, накатывает миграции и прогоняет тесты.
Нужен только Docker. Прогонять **обязательно** после любой правки миграций:
это единственное, что стоит между звонками одной клиентской компании и
другой.

Статус на 2026-08-08: **20/20 проходят** на postgres:17.

## Модель доступа

Каждая таблица несёт `org_id` и закрыта RLS с `force` — то есть политики
действуют даже на владельца таблицы. Единственный, кто их обходит, —
`service_role`, и он живёт только в Worker.

| Роль | Область видимости |
|---|---|
| `owner` | вся организация + биллинг + AI-ключи, самая широкая отчётность |
| `admin` | вся организация, без ключей и биллинга |
| `lead` | только свой отдел |
| `manager` | только свои звонки |
| `viewer` | read-only: свой отдел, а если отдел не задан — вся организация |

Политики не спрашивают `memberships` напрямую — иначе политика на самой
`memberships` уходит в бесконечную рекурсию. Вместо этого всё идёт через
`SECURITY DEFINER`-функции в схеме `app` (`app.user_orgs()`,
`app.user_role()`, `app.can_see_call()`). Менять их — то же самое, что менять
права доступа: только вместе с прогоном тестов.

**Секреты недоступны через data API вообще.** У `org_ai_keys` и
`integration_secrets` нет ни одной политики, поэтому PostgREST не отдаст
оттуда ни строки даже владельцу. Читает их только Worker под `service_role`,
а в интерфейс возвращает лишь `key_hint` вида `…7f2a`.

## Как накатить на живой Supabase

1. Создать **второй бесплатный проект** (первый занят ShipShape).
2. SQL Editor → выполнить по порядку `0001_core.sql`, затем `0002_onboarding.sql`.
   Файлы из `test/` на прод **не накатывать** — там заглушка Supabase и фикстуры.
3. Забрать Project URL, `anon` key и `service_role` key.
4. `anon` — во фронт кабинета, `service_role` — **только** в секреты Worker.
   Если `service_role` окажется в браузере, вся модель доступа обнуляется.

## Что осознанно не сделано

- **Самостоятельной регистрации нет.** Организацию создаёт только Worker
  (`app.create_organization` выдан лишь `service_role`), вход в неё — по
  приглашению. Это снимает вопрос абьюза триала целиком: нет открытой
  регистрации — нечего абьюзить. Когда откроется публичный триал, достаточно
  сменить grant.
- **Биллинга нет** — на пилоте деньги не берём.
- **Аудио не храним** — только текст транскрипта. R2 и расшифровка добавятся,
  когда будет решение по бюджету.
